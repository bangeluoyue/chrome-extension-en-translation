# 项目开发规则（Project Rules）

> 本规则面向 AI 开发助手，作为在本项目中进行开发的统一约束。AI 在编码、拆分任务、提交改动前，都应遵守本规则。
>
> 依据：[技术架构设计文档](../docs/design.md)、[任务拆分](../docs/task.md)。

## 1. 项目定位

- 本项目是一个 **Chrome 浏览器翻译插件**（Manifest V3）。
- 核心链路：从网页提取正文 → 转 Markdown → 调用 AI 大模型翻译 → 打字机展示 → 下载。
- 开发应始终围绕「一键翻译 + 下载」这一核心目标，避免引入需求之外的冗余功能。

## 2. 语言与框架

- **语言**：TypeScript，全项目统一，开启严格模式（`strict`），不滥用 `any`。
- **UI 框架**：React（函数组件 + Hooks）。
- **构建工具**：Vite，支持多入口打包（background / content / popup / 结果页 / 设置页）。
- **Markdown 渲染**：使用 `md-wx` 组件（`MarkdownRenderer`）。
- **内容提取**：`@mozilla/readability` + `turndown`（含 GFM 插件）。
- **AI 调用**：`openai` SDK，通过 OpenAI 兼容协议调用（本项目使用 Qwen）。

## 3. 代码风格

- 统一使用 **ESLint + Prettier**，提交前完成格式化与静态检查。
- 命名约定：
  - 组件文件用 `PascalCase`，其余文件用 `camelCase` 或 `kebab-case`，全项目保持一致。
  - 变量/函数 `camelCase`；类型/接口/组件 `PascalCase`；常量 `UPPER_SNAKE_CASE`。
- 代码注释：用于解释"为什么"，而非复述"做了什么"；复杂逻辑（正文提取、流式渲染）需有说明。
- 函数保持短小、职责单一、可测试。

## 4. NPM 包管理

- **包管理器**：npm（不混用 yarn / pnpm），锁定版本（`package-lock.json` 纳入版本库）。
- **依赖归类**：
  - `dependencies`：运行时依赖（React、`md-wx`、`@mozilla/readability`、`turndown`、`openai` 等）。
  - `devDependencies`：构建与规范类依赖（Vite、TypeScript、ESLint、Prettier 等）。
- **安装原则**：新增依赖需先确认必要性，优先复用已有依赖；不随意升级会导致破坏性变更的版本。
- 依赖安装后需更新 `package-lock.json`。

## 5. 项目目录结构

遵循架构文档约定的目录规范，各模块按职责分层，新增文件应放入对应目录：

```
src/
├── background/     # Service Worker（消息路由、存储）
├── content/        # Content Script（正文提取）
├── popup/          # Popup 入口（React 应用）
├── components/     # 通用 React 组件（md-wx 封装、打字机容器等）
├── services/       # 业务服务（翻译、存储、提取）
├── lib/            # 第三方库封装（Readability、Turndown、OpenAI）
├── types/          # TypeScript 类型定义
└── utils/          # 工具函数
```

- `public/` 仅存放静态资源与 `manifest.json`。
- `docs/` 存放需求、架构、页面布局、任务拆分等文档。

## 6. 架构分层与职责边界

- **Content Script**：只负责页面正文提取（Readability + Turndown），不承担 UI 与业务逻辑。
- **Background Service Worker**：只负责消息路由、存储读写、静态配置读取；**不发起流式翻译请求**（避免 MV3 Service Worker 被回收导致连接中断）。
- **Popup / 结果页 / 设置页**：承担交互与展示；流式翻译请求在**常驻前端上下文**中发起。
- **services**：承载可复用的业务逻辑（翻译、存储、提取），供各入口调用。
- **lib**：统一封装第三方库，隔离外部依赖细节。
- 各层之间**通过统一的消息协议与类型契约通信**，避免跨层直接引用实现细节。

## 7. 数据流与通信约定

- Content Script、Background、Popup 之间通过 Chrome 消息机制通信。
- 消息类型、请求/响应数据结构在 `src/types` 中**集中定义**，禁止使用魔法字符串。
- 与 AI 交互的数据结构（提取结果、翻译请求、翻译结果）单独定义类型，保证跨层一致。
- 本地持久化使用 `chrome.storage.local`，使用**单一存储 Key** 保存"最近一次结果"（无历史记录，仅覆盖更新）。

## 8. 安全与配置

- API Key 等敏感信息**仅存本地**，不硬编码、不进版本库、不打印日志。
- 模型 / Base URL 等参数通过设置页配置，默认使用 Qwen 的 OpenAI 兼容端点。
- 不在代码中写死密钥、内部地址等敏感信息。

## 9. 输出格式约定

- 最终翻译结果需严格遵循需求文档 3.6 节的固定格式：

```
# [文章标题]

> **作者**：[作者名]
> **原文链接**：[原始文章URL]

[翻译后的正文]
```

- 图片统一转换为 `![alt](src)`，翻译过程中不得丢失 Markdown 结构与图片链接。

## 10. AI 助手任务执行规范

为确保开发过程的有序性和可控性，AI 助手必须严格遵循以下任务执行规范：

### 10.1 任务范围控制

- **严格按照任务拆分执行**：必须严格按照 [docs/task.md](../docs/task.md) 中定义的任务范围（T1 ~ T9）执行，不得超出指定任务的边界。
- **单一任务原则**：每次只执行一个明确指定的任务（如"任务 T1"、"任务 T2"等），完成后等待用户确认再进行下一步。
- **禁止自动扩展**：不得基于技术架构文档或其他文档自行扩展任务范围；如需扩展，应先通知用户确认。

### 10.2 任务指令格式

用户应使用以下格式明确指定任务：

- **明确任务编号**：`请执行任务 T3：[正文内容提取]`
- **范围限制**：`只完成任务 T3 中列出的具体任务，不要超出范围`
- **停止指令**：`完成后等待我确认再进行下一步`

### 10.3 执行验收标准

- **任务完成确认**：每个任务完成后，必须对照 [docs/task.md](../docs/task.md) 中的验收标准进行自检。
- **范围边界检查**：确保所有创建的文件和代码都在指定任务范围内。
- **等待用户确认**：任务完成后总结完成情况，等待用户确认后再进行下一个任务。

### 10.4 异常处理

- **任务描述不清晰**：如果任务描述不清晰，应先询问具体范围，而不是自行决定。
- **依赖关系处理**：如果当前任务依赖其他未完成的任务，应明确指出依赖关系并等待用户指示。
- **超出范围的代码**：如果发现已创建超出任务范围的代码，应主动询问是否需要清理。
